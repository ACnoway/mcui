# 轻量化多 Core 主控面板——项目大纲与基础开发流程

> 本文定义产品目标和验收范围。当前实现与后续批次见[阶段 3 进度](./phase-3-progress.md#后续工作)和[分阶段开发流程](./phased-development-workflow.md#4-当前开发顺序)。节点 Token 接入和旧节点迁移见[阶段 1 运维手册](./phase-1-operations.md)。

> 版本：V1.2（实施草案）
> 参考方向：3x-ui 的入站管理、XBoard 的 HTTP 拉取与上报、MMWX 的面板生成 Agent 安装命令。
> 核心目标：**安全优先、轻量部署、Agent 与 Core 解耦、主控集中管理**。

---

## 1. 项目定位与目标

构建一套 **Master（主控）+ Agent（子节点）** 的轻量化代理服务管理平台，统一管理多台服务器上的代理 Core、入站、用户、流量与订阅。

核心原则：

1. **Agent 默认不安装任何 Core**：首次部署只包含 Agent 本体及必要的受限系统组件。
2. **Core 由主控按需下发安装任务**：支持 Xray、sing-box、Mieru 三种类型；Mieru 的服务端进程使用 `mita`。
3. **Agent 与 Core 独立生命周期**：分别升级、启动、停止和卸载；一个节点可安装多个 Core。
4. **主控不转发用户流量**：只负责管理和配置，实际代理流量由节点上的 Core 处理。
5. **在一键部署的前提下提高安全性**。安装器和后台负责配置信任、校验制品和签发任务。认证、权限隔离、审计和回滚随默认部署提供。
6. **避免过度工程化**：早期不引入 Redis、消息队列、Kubernetes，也不做支付及商业化套餐系统。

### 1.1 V1 范围

**范围与优先级口径：**下列功能构成完整 V1。P0 是开发先行且不得豁免的安全门槛；P1 是仍须在 V1 发布前完成的业务功能，不表示可带缺失项发布。若某个 Core 的用户级统计能力未通过锁定版本实测，标记 `UNSUPPORTED`，该 Core 不提供依赖精确流量的额度控制；不得把未知流量当作零。先用一个 Core 完成端到端闭环，再逐个扩展并验证其能力。

- 主控一键脚本和 Docker Compose 安装，支持本地首次登录、配置 HTTPS 反代或主控直连 TLS。
- 单管理员首次初始化、安全登录和多因素认证（MFA）。同一账号管理所有节点、Core 和已实现的业务功能。
- 主控添加节点并生成可独立运行的 Agent 安装命令，支持节点 Token 轮换与撤销、心跳和在线状态。
- 面板选版本安装 Xray、sing-box、Mieru/mita，支持启停、升级、降级与卸载。后台解析和校验制品，默认选择当前节点可安装的最新稳定版。
- SQLite 高频路径使用定向读写，适配资源有限的单机主控。发布提供可验证的安装包、安全补丁和恢复入口。
- 入站配置、用户授权、配置分发及失败回滚（各 Core 能力按实际支持分别实现）。
- 流量采集、额度管理、订阅生成（订阅格式分阶段实现）。
- 安全任务中心、操作审计、配置版本历史、基本节点监控。

**交付顺序。** 先验收单机一键部署和 Xray 实际代理连接，再按相同要求扩展 sing-box 和 mita。完整 V1 以第 12 章的业务和安全验收为准。订阅格式与统计精度按 Core 列出支持范围。

### 1.2 暂不纳入 V1

- 支付、订单、工单、机场商业化运营。
- 任意远程 Shell、SSH 终端或脚本执行。
- 从任意 URL 下载并执行安装包。
- Kubernetes、复杂微服务、Redis / RabbitMQ 等额外依赖。
- 自动 SSH 登录节点部署 Agent、跨平台桌面端。
- 多管理员、委派账号、角色分工和多人审批，纳入后续多用户计划。

### 1.3 主控安装与首次登录

- MCUI 将主控和 Agent 的预构建安装包发布到项目 GitHub Releases。一键脚本校验发布材料后安装主控和面板静态资源。Docker Compose 使用通过相同发布流程构建的版本化镜像，持久化 SQLite、配置和服务密钥。
- 主控安装后默认只允许本机访问，Compose 默认将宿主机端口绑定到回环地址。用户自行配置 HTTPS 反代，或为主控配置证书并显式开放对外监听。反代模式使用明确配置的外部 HTTPS 地址，只信任明确配置的本地或私有代理连接，按外部地址校验请求来源并设置 Secure Cookie。节点接入以 Agent 可访问、可验证的 HTTPS 地址为前提。
- 首次初始化自动生成单个管理员的用户名和高熵初始密码。脚本安装输出到账户操作者的终端，Compose 输出到主控容器的首次启动日志。凭据写入数据库成功后才显示一次。首次登录更换初始密码并绑定 MFA，此后再开放管理操作。重启、升级和挂载已有数据卷继续使用现有身份，本地账号恢复流程负责处理初始化输出丢失的情况。
- 任务签发和认证时间查询随部署配置并接受健康检查。独立检查点按需启用，主控始终保留节点租约核验。面板应能区分节点在线与时间校验失败导致的任务暂停。

## 2. 总体架构

```text
                     ┌────────────────────┐
                     │ 管理员 Web UI      │
                     └─────────┬──────────┘
                               │ HTTPS
                     ┌─────────▼──────────┐
                     │ Master 主控         │
                     │ - 管理员认证 / MFA  │
                     │ - 节点和 Core 管理   │
                     │ - 用户与入站        │
                     │ - 任务与审计        │
                     │ - 配置和订阅生成    │
                     │ - 流量汇总          │
                     └─────────┬──────────┘
                               │ Agent 出站 HTTPS + 节点 Token
            ┌──────────────────┼───────────────────┐
            │                  │                   │
    ┌───────▼────────┐ ┌───────▼────────┐ ┌────────▼───────┐
    │ Agent A        │ │ Agent B        │ │ Agent C        │
    │ 独立进程       │ │ 独立进程       │ │ 独立进程       │
    │ Xray（按需）   │ │ sing-box（按需）│ │ mita（按需）    │
    └────────────────┘ └────────────────┘ └────────────────┘

   客户端直接连接各节点上的 Core；Master 不经过代理数据流量。
```

**部署形态：**

- `panel`：Go 主控单程序；前端资源可通过 `embed` 内嵌。
- `agent`：Go 子节点程序，不内置任何代理 Core。
- `agent-helper`：最小特权组件，负责严格限定的系统级安装/进程操作；不提供通用执行入口。
- `xray` / `sing-box` / `mita`：按主控批准的任务单独安装的外置进程。
- `SQLite`：V1 主控本地数据库，高频认证与状态更新采用索引和定向事务。

## 3. 核心模块

| 模块 | 主控职责 | Agent 职责 | 优先级 |
|---|---|---|---|
| 身份与安全 | 管理员认证、MFA、节点凭据、授权、审计 | 校验主控 HTTPS、保护节点 Token、任务验签和执行约束 | P0 |
| 节点管理 | 注册、禁用、分组、状态管理 | 心跳、系统信息、离线续运行 | P0 |
| 任务调度 | 下发结构化任务、版本与进度管理 | 持久化任务、验签、幂等执行与结果确认 | P0 |
| Core 管理 | 发布版本清单、安装/更新/卸载任务 | 下载、校验、原子安装、进程管理、回滚 | P0 |
| 配置管理 | 渲染 Core 配置、生成 revision | 检查、验证、应用、回报与回滚 | P0 |
| 入站与用户 | 入站模板、用户凭据、入站授权 | 应用到对应 Core | P1 |
| 流量与额度 | 汇总去重、总额度、历史统计 | 增量采集、缓存及补报 | P1 |
| 订阅 | 节点分配、密钥链接、格式输出 | 不提供订阅生成 | P1 |
| 运维监控 | 节点监控、日志与告警 | CPU/内存/进程状态的最小必要上报 | P1 |

### 3.1 统一 Core 适配层

设计 `CoreAdapter`，将不同 Core 的安装、验证、运行、配置与统计能力封装在独立实现中：

```go
type CoreAdapter interface {
    Type() string
    ValidateConfig(ctx context.Context, config []byte) error
    ApplyConfig(ctx context.Context, config []byte) error
    Start(ctx context.Context) error
    Stop(ctx context.Context) error
    Restart(ctx context.Context) error
    Status(ctx context.Context) (CoreStatus, error)
    CollectTraffic(ctx context.Context) ([]TrafficDelta, error)
}
```

Core 的**安装/升级/卸载**更适合由独立的受信任 `CoreManager` 统筹，避免每个适配器自行实现高权限安装逻辑；适配器只实现差异化的配置和运行行为。

- **Xray**：Xray 配置及 API/统计功能。
- **sing-box**：sing-box 配置和版本特定的监控能力；流量统计不可假定所有构建都支持。
- **Mieru**：服务端是 `mita`，需要独立实现配置与用户/配额接口；不能照搬 Xray 的入站和流量模型。
- 使用 `Capabilities` 描述功能差异，UI 对不支持的功能明确禁用。
- 不承诺所有 Core 都可以无中断热重载；按配置类型选择 reload/restart。

### 3.2 用户、入站与节点的关系

```text
Node（节点） 1 ── N CoreInstance（Core 实例）
CoreInstance 1 ── N Inbound（入站）
User（用户） N ── N Inbound（通过 UserInbound 授权）
User 1 ── N TrafficRecord（流量记录）
```

用户额度由主控统一核算；跨多个节点的额度限流为**近实时**，需明确同步延迟和离线策略，不能假定全局瞬时严格一致。

### 3.3 管理面板的授权与会话边界

- V1 由一个管理员在面板管理全部节点和 Core。服务端默认拒绝未授权的操作，逐次核验会话、操作、目标对象及其状态。节点 Token 继续限定在该节点的 API 和资源范围。多用户授权设计见[权限文档](./panel-authz.md)。
- 后台受限签发服务核验允许的操作、精确目标、参数、时限与序号，记录发起者、授权依据和执行结果。管理员在面板确认降级、卸载等高风险操作，并按策略复验 MFA。Agent/Helper 更新保留独立发布与节点更新授权，紧急信任恢复保留受保护的本地入口。
- 管理会话使用服务端可撤销的会话、`Secure`/`HttpOnly` Cookie、受限作用域、空闲及绝对超时；登录和敏感操作有速率限制、MFA 和重新验证。所有改变状态的 Web API 实施 CSRF 防护与来源校验；`SameSite` 仅作纵深防护。限制 CORS，避免把浏览器会话凭据暴露给跨域脚本。
- 管理 UI 对节点上报的主机名、错误信息、日志和配置预览按不可信输入处理；输出编码、避免不受控 HTML、严格 CSP，禁止将密钥放在浏览器持久化存储。API 错误和审计导出都需脱敏。
- 订阅令牌使用高熵随机值，服务端仅存摘要，可撤销/轮换，限制请求频率和响应缓存；令牌不得出现在普通访问日志、错误上报或第三方分析中。订阅端点与管理员 API 分开鉴权，并明确其泄露后处置流程。

### 3.4 配置安全策略

**配置签名只证明授权来源，不证明配置安全。**主控生成配置和 Agent 应用配置时均应按 `(Core 类型, 已验证版本, 节点策略)` 校验允许的配置语义，至少覆盖监听地址与端口、管理 API、文件读写路径、外部规则/资源 URL、日志输出、出站目的及敏感凭据引用。禁止通过配置引入任意本地文件读取、任意命令、向公网暴露本地管理 API 或绕过节点隔离。不能安全解释的字段或新版本能力默认拒绝；能力矩阵与配置策略随锁定版本更新。预检应在受限环境运行，不把未信任的候选二进制当作验证工具。

## 4. Agent 设计：默认空安装

### 4.1 首次部署流程

1. 管理员在主控「节点管理」添加节点。主控分配 `node_id` 并显示「待接入」。
2. 管理员打开该节点的「生成安装命令」。主控签发绑定此节点的短期一次性安装码，生成包含主控 HTTPS 地址、节点 ID 和安装码的可复制命令。
3. 管理员在受支持的 Linux/systemd 节点执行这一条命令。安装程序识别架构、准备依赖、验证 GitHub Releases 上的安装包，安装 Agent 和最小特权 Helper，并自动配置任务公钥、key ID 及部署需要的 CA。通过已验证的 HTTPS 兑换该节点的独立 Token，持久化身份并启动服务。
4. Agent 首次心跳成功后，主控在原节点记录显示「在线」，管理员即可选择 Core 和版本。安装失败时提供可重试的入口，重装、升级和轮换沿用原节点身份及有效账本。

MCUI 发布信任应能独立于面板下载响应验证。命令锁定批准的安装程序并在提权前检查安装制品，节点侧完成信任配置和服务安装。Agent 主动连接主控，节点仅按需开放 Core 的代理入站端口。

### 4.2 本地运行布局（建议）

```text
/opt/lightpanel/
├── agent/                 # Agent 二进制
├── cores/
│   ├── xray/versions/
│   ├── sing-box/versions/
│   └── mieru/versions/    # mita 服务端
├── configs/               # 版本化配置
├── state/                 # 任务、上报队列和当前配置状态
└── logs/                  # 不记录敏感凭据
```

实际布局中，凭据应存放在**仅 Agent 用户可读的受限目录**，不要把密钥混入通用日志或共享配置目录。Core 进程可分别配置为低权限系统用户运行。

## 5. Core 安装与更新的安全流程

```text
管理员选择 Core 和版本，或对已安装实例发起操作
   ↓
主控鉴权、按操作复验或明确确认、解析节点与制品
   ↓
后台受限签发器生成指定节点的签名任务
   ↓
Agent 拉取并验证：身份、签名、类型、有效期、序号
   ↓
根据可信发布清单解析固定版本、架构、摘要
   ↓
通过受信任源下载到临时目录（限制大小和超时）
   ↓
验证清单签名、制品摘要、内容与目标架构
   ↓
拒绝路径穿越 / 符号链接逃逸 / 非法文件权限
   ↓
受限 Helper 原子安装到版本目录
   ↓
验证配置、启动或安全切换并执行健康检查
   ↓
提交成功；失败时回滚并保留审计记录
```

**关键约束：**

- 安装页面的必选项为版本。在所选节点、Core 和架构下，`latest` 指当前有效签名清单中可安装的最新稳定版，页面显示实际版本号。安装列表只包含可用版本，允许少量受控可选参数。启停与升级所需的当前版本从节点状态取得，SHA-256、文件名、架构和清单版本由程序自动解析。
- 安装任务只允许预定义 Core 类型、受支持架构和经过批准的固定版本。
- **不允许主控提供任意 Shell 命令或任意下载 URL**。
- 下载后的 SHA-256 校验应由**独立可信的签名发布清单**绑定；如果摘要和文件都来自未经验证的同一来源，不能证明真实性。
- Core 使用固定官方发布仓库的原始二进制包。上游提供签名时进行验证，MCUI 发布方在审核后用签名清单绑定精确字节、版本、长度和架构。备用缓存保存同一官方制品，节点按同一清单复验。
- 原子安装与版本切换须防止半更新状态；健康检查失败回滚到上一稳定版本。
- Agent、Helper 本身的更新也必须采用签名校验和回滚机制。
- Agent/Helper 自更新使用独立于日常 Core 任务的发布授权与人工恢复预案：先安装到不可变新版本，启动健康确认后提交，超时自动回到 LKG；Helper 不直接覆盖正在运行的自身。未完成此路径的故障演练前，不开放远程自更新。
- 卸载默认保留必要的审计元数据；用户数据和配置删除策略需明确。

### 5.1 支持的 Core

| 主控展示 | 实际服务端程序 | 初始目标 |
|---|---|---|
| Xray | `xray` | 安装、配置、进程与用户统计 |
| sing-box | `sing-box` | 安装、配置、进程与可用统计能力 |
| Mieru | `mita` | 安装、服务端配置、用户/配额管理 |

可以允许一台节点同时存在三套 Core，但每个实例需要独立端口、配置、进程身份和资源限制，并校验端口冲突。

## 6. 安全威胁模型与强制要求

| 风险 | 最低安全措施 | 验收方式 |
|---|---|---|
| 伪造 Agent / 主控 | 验证主控 HTTPS、一次性安装码、单节点 Token、应用层撤销 | 拒绝伪造主控、无效或撤销 Token 及跨节点访问 |
| 重放 / 篡改任务 | 任务签名、节点绑定、过期时间、单调序号、持久化去重 | 重放旧任务被拒绝 |
| 主控越权管理 | 对象级授权、管理员 MFA、高危操作复验与审计 | 越权 API 请求被拒绝并记录 |
| 远程命令注入 | 仅允许结构化任务；Agent/Helper 无通用 shell 执行接口 | 恶意参数不能转化成命令 |
| 恶意或被替换的 Core 包 | 可信签名清单、制品哈希、固定版本、严格解包 | 篡改制品无法安装 |
| Agent 提权 / Core 逃逸 | Agent 非 root，最小特权 Helper，独立用户与 systemd 限制 | 常规进程不能写系统敏感目录 |
| 配置泄露与订阅滥用 | 敏感字段加密、权限隔离、日志脱敏、订阅令牌可撤销 | 日志/普通 API 不泄露凭据 |
| 配置错误 / 升级故障 | 预检、原子切换、健康检查、保留上一版本 | 失败后恢复旧版本 |
| 流量上报重复 / 丢失 | 批次 ID、序号、服务端去重、Agent 本地待确认队列 | 重试不重复累计，断线后可补报 |
| 管理面暴露风险 | HTTPS、安全 Cookie、CSRF/CORS/CSP、限流、依赖扫描 | 基础 Web 安全测试通过 |
| 已签名但越权的配置 | 逐 Core/版本的语义允许范围、节点侧复验 | 外露管理 API、越界路径、远程资源等配置被拒绝 |
| 签发服务滥用 | 操作白名单、对象权限、精确参数绑定、签名密钥隔离 | 拒绝未授权操作、跨节点改参和重复执行 |

### 6.1 关键权限边界

- **Web 管理端**：仅向主控提交受控管理请求，不能直接操作节点操作系统。
- **Master**：决定允许执行什么任务，维护审计、授权及版本配置；任务签名密钥需保护并与普通应用权限隔离。
- **签发服务**：只签经核验且符合签发策略的规范化任务。任务签名密钥和发布私钥分离，普通 Web 进程无法直接读取这两类私钥。
- **Agent**：仅验证并执行已授权的任务，记录本地状态；不能执行不受约束的命令。
- **Helper**：拥有有限特权，只能操作固定服务和经过验证的安装目录。
- **Core 进程**：低权限运行，不允许读取 Agent/主控凭据。

**安全边界说明。** 主控失陷可能影响各节点。设计应通过受限签发、固定 Helper 操作、节点独立验签和可信制品限制影响范围。

## 7. 主控与 Agent 通信协议（初版）

采用 **普通 HTTPS + 节点 Token + JSON**。Agent 校验主控服务端证书链和主机名，默认使用系统 CA，使用私有 CA 时可在节点侧显式配置。主控只需部署服务端 HTTPS 证书。Agent 主动轮询任务和配置，并上报心跳、执行结果与增量流量。HTTP 拉取和上报参考 [XBoard UniProxy 路由](https://github.com/cedar2025/Xboard/blob/master/app/Http/Routes/V1/ServerRoute.php)，面板生成命令的交互参考 [MMWX Agent 部署](https://miaomiaowux.com/docs/install-agent/)。

| API | 用途 |
|---|---|
| `POST /api/v1/agent/enroll` | 用一次性安装码换取已建节点的 `node_id` 与 `node_token` |
| `POST /api/v1/agent/heartbeat` | 更新节点在线状态与版本信息 |
| `GET /api/v1/agent/tasks/next` | 拉取本节点下一条任务或控制消息 |
| `POST /api/v1/agent/tasks/ack` | 确认任务状态、执行结果或错误 |
| `GET /api/v1/agent/config` | 按 revision 拉取本节点配置 |
| `POST /api/v1/agent/traffic` | 幂等上报增量流量批次 |
| `POST /api/v1/agent/health` | 上报 Core 与资源指标 |

注册后的请求通过 `Authorization: Bearer <node_token>` 认证。主控根据 Token 确定 `node_id`，逐请求检查节点启用状态与资源归属。安装码使用一次即失效，明文仅在生成命令时展示。主控只存安装码与 Token 的摘要，Agent 将 Token 写入受限文件，URL、日志和错误信息均不携带凭据。

安装请求示例：

```http
POST /api/v1/agent/enroll
Content-Type: application/json

{"install_code":"<one-time-install-code>"}
```

重新接入时，管理员为原节点生成新命令。新 Token 生效时旧 Token 同步失效。发现泄露时可先禁用节点并撤销凭据。现有 mTLS 节点切换时沿用原 `node_id` 并保留任务账本和序号，切换后拒绝旧客户端证书鉴权。详见[Agent 协议第 2 节](./agent-protocol.md#2-节点接入token-轮换和撤销)。

签名任务格式见[Agent 协议](./agent-protocol.md)。Agent 仍需验证签名、目标节点、时效和序号。Helper 独立校验原始签名授权与实际参数，在 root 私有账本记录已执行的高权限副作用。

### 7.1 任务状态机

```text
PENDING → DELIVERED → RUNNING → SUCCEEDED
                      └───────→ FAILED → ROLLED_BACK（适用时）
          └────→ EXPIRED / CANCELED（仅在未开始或可安全中止时）
```

- 任务必须**幂等**，重复领取不会重复执行危险操作。
- 状态在 Agent 本地持久化，重启后能够恢复或安全终止。
- ACK、执行结果和状态变化均记录审计事件。
- 配置使用 `revision` / 哈希标识，避免旧版本覆盖新版本。

### 7.2 初始通信周期（可配置）

| 任务 | 默认周期 |
|---|---:|
| 心跳 | 15 秒 |
| 检查任务 / 配置版本 | 15 秒 |
| 上报增量流量 | 30 秒 |
| 在线超时判定 | 60 秒无心跳 |

## 8. 基础数据模型

V1 可先采用以下表：

```text
admins
admin_sessions
nodes
node_credentials
core_instances
core_artifacts
core_versions
inbounds
users
user_inbounds
agent_tasks
config_revisions
traffic_reports
traffic_daily
audit_logs
settings
subscription_tokens
security_events
```

关键约束：

- `core_instances`：节点、Core 类型、安装版本、运行状态、配置版本。
- `core_artifacts`：固定版本/架构、摘要、可信清单标识、签名验证信息。
- `agent_tasks`：任务 ID、目标节点、类型、序号、签名、状态和审计时间。
- `traffic_reports`：按节点 + 批次唯一约束，保证重复提交不重复计量。
- `config_revisions`：保留历史版本、摘要、发布时间、应用结果和回滚版本。
- `node_credentials`：安装码与节点 Token 的摘要、节点归属、状态、安装码有效期及撤销记录。
- `subscription_tokens`：仅存令牌摘要、范围、有效期和撤销状态；不在日志中写明文令牌。

主控数据库、审计事件、节点凭据和签名信任状态使用受限备份与保留期限。恢复须核对序号、撤销和防回退状态，出现不确定性时暂停受影响的变更并对账。独立检查点提供可选的整库防回滚保护。

### 8.1 低配主控的数据库要求

节点 Token 鉴权按摘要索引查询，心跳在单行更新中复核 Token 和禁用状态。数据库迁移为已有节点补建索引。其他 `Store.Update` 路径仍读取完整状态并重写多张表，后续覆盖会话续期和审计追加。流量记录按保留周期汇总。为管理视图保留分页，避免请求开销随历史审计量增长。

任务协调锁只覆盖需要串行化的状态转换。读取 HTTP 请求、等待签发和传输包字节应在锁外执行。迁移须保留已有数据库、凭据、会话撤销和任务账本，并验证单机与启用独立检查点时的事务和恢复语义。验收记录低配环境规格、节点数、并发心跳期间的面板响应、资源占用和写盘量，同时验证撤销生效和任务互斥。

## 10. 基础开发流程（分阶段）

阶段依赖和发布条件见[分阶段开发流程](./phased-development-workflow.md)。当前批次及完成条件见[阶段 3 后续工作](./phase-3-progress.md#后续工作)。

0. 设计基线：协议、威胁模型、权限、制品信任及支持目标。
1. Master 与空 Agent：身份、会话、主控添加节点并生成安装命令、Token 鉴权与撤销、只读节点信息。
2. 签名任务与只读 Helper：验证授权、防重放、状态反馈和重启恢复。
3. Xray 生命周期：复用可信安装、启停和回滚，改为单管理员在面板选版本并发起操作。
4. Xray 完整闭环：先完成受控入站和真实客户端连接，再补齐用户、可用统计、额度与订阅。不可靠统计标记 `UNSUPPORTED` 并禁用精确额度。
5. 安装与 Docker 构建：与 Xray 闭环并行开发主控安装、首次登录和 Agent 一键接入。先优化心跳路径，再完成数据库和任务锁优化。
6. sing-box 与 mita：复用 Xray 经验，逐版本完成生命周期、业务、兼容性和隔离验证。
7. 完整 V1 验收和发布：安全测试、故障演练、恢复及运行手册。

Xray 的实际代理连接用于验收首批部署链路。完整 V1 的各 Core 能力以实测矩阵为准。

## 12. V1 验收清单

Debian 13.7 amd64 使用 `ro` 的隔离环境执行运行和故障验证。Linux arm64 验证构建。

1. **主控部署**：在空环境分别用一键脚本和 Compose 安装。检查回环默认监听、HTTPS 反代和直连证书、仅首次输出初始凭据、首次登录换密和 MFA，以及重启与升级保留身份。
2. **节点接入**：在受支持的干净节点运行一条命令，自动配置发布信任、Agent 和 Helper。首次心跳使原节点上线，Core 保持未安装。验证中断重试、安装码重用、Token 撤销和跨节点访问。
3. **受控安装**：同一管理员在面板选择版本，安装 Xray、sing-box、mita 并执行启停、更新、降级和卸载，后台解析摘要并记录任务。至少验证 Xray 的真实客户端连接及失败回滚，再扩展到其他 Core。
4. **制品验证**：篡改或不在批准清单中的安装包无法安装。
5. **隔离运行**：Agent 及各 Core 以最小权限运行，Helper 无通用 Shell 能力。
6. **配置管理**：可创建入站/用户，配置正确下发；错误配置可回滚。
7. **多 Core 共存**：同一节点可管理多个 Core，并阻止端口冲突。
8. **主控失联容错**：主控断开时已有 Core 继续服务；恢复后补报流量。
9. **流量一致性**：重试上报不会重复累计，订阅与用户授权正确。
10. **高危操作防护**：安装、卸载、密钥轮换等操作有权限验证和审计。
11. **管理面授权**：所有管理 API 做服务端操作与对象级鉴权；越权、CSRF、会话撤销和敏感操作复验测试通过。
12. **配置约束**：签名但违反节点配置策略的内容也被拒绝；错误配置不破坏 LKG。
13. **自身更新**：Agent/Helper 远程更新的独立签名、健康确认、断电回滚与本地人工恢复演练全部通过；在通过前仅能作为内部安全底座验收，不得称作完整 V1。
14. **统计与订阅**：逐 Core 明确统计口径和支持范围，订阅令牌可撤销且不进入普通日志；不能计量的 Core 不宣称精确额度能力。
15. **低配主控**：并发心跳和任务请求下，管理面保持可用。验证高频路径的定向读写、撤销即时生效和互斥语义，记录环境与结果。
16. **补丁交付**：扫描 Go、前端、镜像和支持的 Core 版本。验证签名补丁可安装，失败可恢复，升级保留身份与账本。

## 13. 项目开发纪律

- **安全与可恢复性优先于功能数量。** 每个新模块必须附带权限、错误恢复和审计设计。
- **主控无任意命令执行能力。** 任务接口只接受受限结构化操作。
- **先做一个 Core 的完整闭环，再横向扩展。** 推荐先 Xray，再 sing-box，最后 Mieru/mita；但底层协议从第一天就面向多 Core。
- **版本明确、功能明确、失败明确。** 不支持的 Core 特性在 UI 明示，不假装成功。
- **先单机轻量、后扩展。** V1 使用 Go + Vue + SQLite + systemd，只有确实遇到规模瓶颈再引入额外基础设施。
- **关注上游许可证和发行方式。** 引用、修改或分发 Xray、sing-box、Mieru 以及参考项目源码时，逐项确认许可证、NOTICE、发布产物和合规义务。
