## 2. 依赖及工具链锁定规则

- 编码前由维护者评审并明确精确 Go 工具链、Node 和包管理器版本、来源、支持期限及更新负责人；不要把本机发现的版本默认为批准版本。需要的 Linux/systemd、amd64/arm64 版本及 Core 版本、构建选项、来源和能力在阶段 0 支持矩阵中另行冻结，未经实测不得标记支持。
- Go 工程建立后提交 `go.mod` 和 `go.sum`，锁定直接/传递依赖及校验信息；禁用隐式工具链漂移，CI 使用已批准的精确工具链。CI 在干净检出上以只读模块模式执行检查，并核验依赖文件未被改写；模块更新须单独评审。
- 前端建立后选定一种包管理器、固定其版本，提交对应唯一 lockfile（若选 pnpm 则为 `pnpm-lock.yaml`）；CI 使用该版本的冻结锁文件安装，拒绝自动改锁或混用 lockfile。禁止浮动版本、未审查的远程脚本；安装脚本权限、网络和机密隔离须评估。
- 第三方 CI action、构建镜像和工具按不可变完整提交 SHA 或镜像摘要固定；记录来源、许可证、完整性和变更原因。依赖升级通过专门变更展示锁文件差异、漏洞和兼容性测试；漏洞扫描发现阻断问题时修复或停止交付，不以静默忽略代替决议。
- Core 制品不是普通构建依赖：固定来源、版本、架构、摘要、构建选项及受信签名清单；发布信任和降级授权以阶段 0 制品信任协议最终决议为准。任务签名与发布根密钥隔离。

## 3. CI 设计要求（尚未实施）

仓库已有 Go/Vue 工程和 [`scripts/check-static.sh`](../scripts/check-static.sh)，但尚无自动 CI 工作流或已核实的分支保护。所有合并请求和受保护主分支仍须在 CI 建成后运行与变更相匹配的强制检查；缺少工作流、失败、跳过、过期或无结果均不视为通过。最少包含：

1. 干净环境检出固定提交，验证精确工具链与锁文件；Go 格式、`go vet`、单元/集成测试及适用平台的 `go test -race`；前端冻结安装、类型检查、lint、单元测试和构建。具体命令在工程脚本和 CI 建立时固化，不把不存在的脚本视作已通过。
2. 每个协议和安全边界有正反例；任务解析、规范化/签名、归档和 Helper 请求逐步加入 fuzz，固定种子与失败样例可重现。权限、依赖漏洞、密钥泄露和许可证检查按风险纳入；构建输出生成 SBOM 并可追溯到提交、依赖和工具链。
3. PR 不接触发布私钥或生产凭据，尤其不可信 fork；CI 最小权限、隔离执行、限时，避免执行未经审查的第三方代码并暴露机密。发布使用隔离的授权流程、签名及审计，禁止 PR 直接发布。
4. CI 保存提交 ID、工具版本、测试与扫描结果、失败日志及制品摘要，日志脱敏；架构矩阵、干净 Linux VM 与 systemd 实测不能仅由交叉编译替代。流水线及分支保护规则须实际配置、核验并由维护者记录，本文不是已启用证明。

## 4. 评审与变更控制

- 每次变更通过 PR/MR，至少一名非作者审阅并批准；保护主分支，要求必需检查通过、禁止直接推送和自我批准。涉及身份、授权、签名、Helper、制品、配置策略及恢复的变更还需非原实现者安全评审；信任根变更至少双人审批，不用代码批准代替运行时审批。
- 描述目的、威胁与权限边界、协议/兼容性和迁移、测试证据、日志脱敏、回滚或人工恢复、关联决议及未解决风险；依赖或 CI 权限变化单列审查。协议变化同步跨实现测试向量与版本协商。
- 未解决的阻断意见或失败门禁不得合并；其他风险须记录责任人、影响、到期时间和明确接受者，不能豁免 P0、绕过阶段退出条件或以 UI 隐藏代替修复。对发现严重问题的变更停止发布并复核。

## 5. 阶段 0 验证与后续门禁

阶段 0 的验证是**文档与决议验证**，不是运行产品测试。负责人按以下条目收集证据和评审结论；未完成为阻断，不得标为阶段 0 已退出：

- [ ] 按[阶段流程阶段 0](./phased-development-workflow.md)逐项核对架构、威胁、权限矩阵、身份协议、任务 schema/签名/序号/恢复、Helper 固定操作、配置策略、制品信任与支持矩阵；明确密钥持有人、审批、恢复和失陷后果。
- [x] 生成任务/配置/取消/跳过共享正反向量，并由 Go 与 Node.js 两种实现校验规范化签名字节和签名；向量与验证器位于 `internal/protocol/testdata/protocol-v1.json`、`internal/protocol` 和 `scripts/verify-protocol-vectors.mjs`。该结果不冻结序号/租约/恢复语义，也不代替独立安全评审。
- [ ] 确认不存在任意 Shell、URL、路径或 Unit 操作；记录所有未决项、冲突、责任人和解决证据。发布信任采用 TUF 或签署简化方案差异与风险；明确离线过期、回滚、根轮换和恢复。
- [ ] 完成本文的依赖、CI、评审、威胁测试计划评审，并为下一阶段建立可执行验收任务；由阶段负责人和独立安全评审者记录评审人、日期、文档版本/提交、结论及证据链接。

**后续门禁：**阶段 1 仅空 Agent 和只读面板，须证明注册、撤销、服务端对象授权、会话安全及离线续运行；阶段 2 须证明签名/重放/Helper 独立授权和重启对账；阶段 3–4 须证明制品可信、LKG、自更新恢复及各 Core 隔离；阶段 5–6 须证明配置语义约束、恢复、统计去重及订阅撤销；阶段 7 完整安全/故障演练与独立审查。每阶段具体退出条件以阶段流程为准，不可用本文摘要替代。

每次验收记录范围、构建/提交、环境、测试命令与结果、证据、执行者、复核者、未决风险和结论；失败或未执行均非通过。完整 V1 需 P0 和 P1 均满足，三种 Core 的锁定能力和限制公开，无法可靠统计标为 `UNSUPPORTED` 并禁用精确额度；存在未解决 P0 安全缺陷不得发布。

## 6. 最小威胁测试清单（分阶段执行；证据见实施状态记录）

每项应在对应阶段实现自动化或可复现实机测试，记录正例、攻击输入、预期拒绝及无副作用证据；当前仅有一部分 Phase 1 API 集成测试，不能视为完整矩阵通过。详细范围不替代 [Agent 安全测试矩阵](./agent-technical-design-v1.0.md)。

| 阶段 | 威胁/用例 | 最低预期 |
|---|---|---|
| 1 | 伪造 Master、未注册/撤销节点、重复邀请、证书轮换；跨对象读取、会话撤销、CSRF/XSS | 拒绝伪造和越权，不泄露数据；撤销后失效，不可信文本安全编码 |
| 2 | 修改签名任务、目标、时效、序号，重放、取消与租约竞争、伪造审批 | 拒绝未授权请求；重启对账后无重复特权副作用，序号缺口有明确恢复 |
| 2 | 其他用户调用 Helper、篡改实际参数、任意命令/路径/Unit | Helper 独立拒绝；系统与非目标服务无变化 |
| 3–4 | 篡改/过期清单、错误摘要/架构、路径穿越/链接/归档炸弹 | 拒绝安装，受控目录及 LKG 不变 |
| 3–4 | 断电、磁盘满、启动失败、自更新失败；Core 横向读取 | 经实机核验恢复或明确安全停机；隔离阻止读取其他凭据 |
| 5 | 已签名但越权配置、旧 revision、越界路径、暴露管理 API | 策略拒绝且不改变 LKG；仅目标节点/Core 可变更 |
| 6 | 重复批次、断线补报、计数重置、订阅撤销及令牌进入日志 | 不重复累计，缺口可见；撤销生效，日志不含令牌 |
| 7 | 24 小时主控离线、备份恢复、重启、时钟回退及密钥恢复 | 按策略保持或安全停机，状态可对账；无法证明新鲜时停止高危签发 |

阶段 7 还须完成全量授权、fuzz/race、依赖扫描、SBOM、签名发布、故障演练及独立安全代码审查；失败、无证据或未执行均阻断对应验收。
