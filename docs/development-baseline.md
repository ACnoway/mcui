## 2. 依赖及工具链锁定规则

- 工具链基线更新为 Go `1.27.4`、Node.js `26.13.1`、pnpm `12.17.0`（按 2026-11-16 官方最新补丁锁定）。Go 1.27.4 的发布记录包含 TLS/HTTP 等安全修复；Go 项目仅支持最近两个主要版本，故 1.24 已不适合作为当前基线。Node 26.13.1 是 LTS 安全更新；pnpm 12.16.0 修复了 zstd 处理与签名相关安全问题，基线锁到后续的 12.17.0。参见 [Go Release History](https://go.dev/doc/devel/release)、[Node.js 26.13.1](https://nodejs.org/en/blog/release/v26.13.1)、[pnpm 12.16.0 security fixes](https://pnpm.io/blog/releases/12.16.0) 和 [pnpm 12.17.0](https://pnpm.io/blog/releases/12.17.0)。`scripts/check-static.sh` 强制精确值，`.nvmrc` 与 `web/package.json` 记录 Node/pnpm 版本。维护者仍须设定更新负责人和生命周期更新节奏，不能因版本固定而长期停更。
- Go 工程提交 `go.mod` 和 `go.sum`；CI 的 Go 版本精确固定，构建/测试后核验依赖文件未被改写。模块更新须单独评审。
- TUF 客户端依赖固定为 `github.com/theupdateframework/go-tuf/v2 v2.4.2`；生产 root/targets 密钥、发布仓库、发布签核及互操作测试仍未完成。Core 制品验证不能因 Go 包已接入就被视作启用。
- 前端只使用 `pnpm-lock.yaml`；CI 运行冻结锁文件安装并核验未改写。禁止浮动版本、未审查的远程脚本；安装脚本权限、网络和机密隔离须评估。
- 第三方 CI action、构建镜像和工具按不可变完整提交 SHA 或镜像摘要固定；记录来源、许可证、完整性和变更原因。依赖升级通过专门变更展示锁文件差异、漏洞和兼容性测试；漏洞扫描发现阻断问题时修复或停止交付，不以静默忽略代替决议。
- Core 制品不是普通构建依赖：固定来源、版本、架构、摘要、构建选项及受信签名清单；发布信任和降级授权以阶段 0 制品信任协议最终决议为准。任务签名与发布根密钥隔离。

## 3. CI 配置与仓库门禁

仓库已有 [`.github/workflows/static-checks.yml`](../.github/workflows/static-checks.yml) 和 [`scripts/check-static.sh`](../scripts/check-static.sh)。工作流使用只读仓库权限、固定完整 SHA 的 actions、`ubuntu-24.04` 和已锁定工具链；检查 Go 格式/vet/build/test、amd64/arm64 Linux 交叉构建、协议向量、冻结 pnpm 安装和 Vue 生产构建。工作流文件本身不证明目标提交上的远程检查已运行并通过，也不证明远端仓库规则已配置并生效。

1. 当前 CI 干净检出固定提交，验证精确工具链与锁文件；Go 格式、`go vet`、单元/集成测试与跨架构构建；前端冻结安装、类型检查和构建。race、lint、前端单测、依赖漏洞扫描、许可证门禁和 SBOM 尚未接入。
2. 每个协议和安全边界有正反例；任务解析、规范化/签名、归档和 Helper 请求逐步加入 fuzz，固定种子与失败样例可重现。权限、依赖漏洞、密钥泄露和许可证检查按风险纳入；构建输出生成 SBOM 并可追溯到提交、依赖和工具链。
3. PR 不接触发布私钥或生产凭据，尤其不可信 fork；CI 最小权限、隔离执行、限时，避免执行未经审查的第三方代码并暴露机密。发布使用隔离的授权流程、签名及审计，禁止 PR 直接发布。
4. CI 保存提交 ID、工具版本、测试与扫描结果、失败日志及制品摘要，日志脱敏；架构矩阵、干净 Linux VM 与 systemd 实测不能仅由交叉编译替代。流水线和实际采用的仓库规则须核验并由维护者记录，本文不是已启用证明。

## 4. 评审与变更控制

- 默认直接在 `master` 开发，按功能拆分为小而完整的提交；推送前运行与改动相适应的检查。大型或试验性工作可使用临时分支，不强制 PR。变更记录目的、风险和验证结果；涉及身份、授权、签名、Helper、制品、配置策略及恢复的变更进行项目内安全检查。信任根变更至少双人审批，不用代码批准代替运行时审批。
- 描述目的、威胁与权限边界、协议/兼容性和迁移、测试证据、日志脱敏、回滚或人工恢复、关联决议及未解决风险；依赖或 CI 权限变化单列审查。协议变化同步跨实现测试向量与版本协商。
- 未解决的阻断意见或失败门禁不得合并；其他风险须记录责任人、影响、到期时间和明确接受者，不能豁免 P0、绕过阶段退出条件或以 UI 隐藏代替修复。对发现严重问题的变更停止发布并复核。

- [x] 生成任务/配置/取消/跳过共享正反向量，并由 Go 与 Node.js 两种实现校验规范化签名字节和签名；向量与验证器位于 `internal/protocol/testdata/protocol-v1.json`、`internal/protocol` 和 `scripts/verify-protocol-vectors.mjs`。向量验证编码和签名；序号/租约/恢复语义作为设计基线单独记录，运行时行为仍须测试。
- [x] 代码和文档未开放任意 Shell、URL、路径或 Unit API；发布信任已选择 TUF 基线，列明离线失败关闭、回滚、根轮换和恢复策略。TUF 客户端基础已实现，但生产密钥托管、发布仓库及节点集成未实现。
- [x] 已配置基础 CI 和阶段验收计划。项目负责人记录文档版本、提交、检查人、日期、结论与未决风险；检查结果尚待记录。

如需配置远程仓库规则，应由管理员验证其允许本项目默认直接在 `master` 开发的工作流；本地 CI YAML 不代表远端规则已经启用。

**后续门禁：**阶段 1 仅空 Agent 和只读面板，须证明注册、撤销、服务端对象授权、会话安全及离线续运行；阶段 2 须证明签名/重放/Helper 独立授权和重启对账；阶段 3 验证 Xray 制品、LKG 和自身更新恢复；阶段 4 验证 Xray 配置、用户、连接、可用统计与订阅并完成演示；阶段 5 验证安装与 Docker 构建；阶段 6 逐个验证其他 Core 的业务及隔离；阶段 7 完成安全测试与故障演练。每阶段具体退出条件以阶段流程为准，不可用本文摘要替代。

## 6. 最小威胁测试清单（分阶段执行；证据见实施状态记录）

每项应在对应阶段实现自动化或可复现实机测试，记录正例、攻击输入、预期拒绝及无副作用证据；当前仅有一部分 Phase 1 API 集成测试，不能视为完整矩阵通过。详细范围不替代 [Agent 安全测试矩阵](./agent-technical-design-v1.0.md)。

| 阶段 | 威胁/用例 | 最低预期 |
|---|---|---|
| 1 | 伪造 Master、未注册/撤销节点、重复邀请、证书轮换；跨对象读取、会话撤销、CSRF/XSS | 拒绝伪造和越权，不泄露数据；撤销后失效，不可信文本安全编码 |
| 2 | 修改签名任务、目标、时效、序号，重放、取消与租约竞争、伪造审批 | 拒绝未授权请求；重启对账后无重复特权副作用，序号缺口有明确恢复 |
| 2 | 其他用户调用 Helper、篡改实际参数、任意命令/路径/Unit | Helper 独立拒绝；系统与非目标服务无变化 |
| 3、6 | 篡改/过期清单、错误摘要/架构、路径穿越/链接/归档炸弹 | 拒绝安装，受控目录及 LKG 不变 |
| 3、6 | 断电、磁盘满、启动失败、自更新失败；Core 横向读取 | 经实机核验恢复或明确安全停机；隔离阻止读取其他凭据 |
| 4、6 | 已签名但越权配置、旧 revision、越界路径、暴露管理 API | 策略拒绝且不改变 LKG；仅目标节点/Core 可变更 |
| 4、6 | 重复批次、断线补报、计数重置、订阅撤销及令牌进入日志 | 不重复累计，缺口可见；撤销生效，日志不含令牌 |
| 7 | 24 小时主控离线、备份恢复、重启、时钟回退及密钥恢复 | 按策略保持或安全停机，状态可对账；无法证明新鲜时停止高危签发 |

阶段 7 还须完成全量授权、fuzz/race、依赖扫描、SBOM、签名发布、故障演练及项目内安全检查；失败、无证据或未执行均阻断对应验收。
