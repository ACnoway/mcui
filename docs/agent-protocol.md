# Agent 身份、任务与配置协议（阶段 0 设计稿）

> 状态：本文仍是待人工安全评审的协议设计稿。部分 V1 签名对象 schema、严格解析、JCS/Ed25519 校验及共享测试向量已实现于 `internal/protocol`；该包未连接 Master/Agent 运行时。本文细化[分阶段流程](./phased-development-workflow.md)与[Agent 技术设计](./agent-technical-design-v1.0.md)；旧示例 JSON 仅作示意。Phase 1 只有空 Agent 身份与节点/审计读取，没有任务投递、执行或节点副作用接口。

## 1. 信任边界与基本约束

Agent 主动 HTTPS Pull，不提供入站管理端口；正常管理请求使用 mTLS，证书身份从 TLS 连接得出，绝不信任请求体自报身份。Master Web、签发服务、Agent、root Helper、Core 为独立边界。签发服务独立持有任务/配置签名私钥；发布根、节点 CA、任务和配置密钥相互独立。Web 不直接持有签名私钥。高危操作经服务端对象鉴权、复验与独立审批；信任根变更至少两名不同授权人批准。审批绑定操作、节点、规范化参数摘要、期限和用途，签发服务重新核验并原子消费；`approval_id` 自身不是审批证明。

任何签名都不能代替配置语义策略、可信制品验证或 Helper 独立授权。禁止任意 Shell、脚本、URL、文件路径、unit 和 argv；未知类型、字段、策略一律拒绝。主控离线或认证失败时不接收新授权，默认保留运行中的 LKG；已开始事务只能依照下文恢复。完全控制合法签名者或节点 root 仍可能破坏安全。

## 2. 注册、mTLS、轮换和撤销

1. 安装包不含 Core。通过独立可信渠道预置 Master 服务端 CA 根及正确 DNS 名称、任务和配置验证公钥及其 key ID；禁止首次连接信任（TOFU）、关闭证书/主机名验证或用邀请引导信任。连接仅 TLS 1.3，验证完整证书链、有效期、serverAuth 和 DNS SAN；不跟随重定向。根信任材料须通过已验证的发布渠道分发。
2. 授权管理员创建限定节点组/用途、短期有效、一次性高熵随机邀请；服务端仅保存密码学摘要，限速、限制尝试并审计，不记录明文。Agent 本地生成独立私钥及 PKCS#10 CSR，私钥不离开节点，文件仅专用 Agent 账户可读或使用硬件保护。
3. `POST /api/v1/agent/enroll` 仅服务端 TLS：传邀请、CSR 及注册请求 ID；服务端验证 CSR 自签名证明私钥持有，校验邀请及审批策略。审批通过后事务性分配不可复用 `node_id`、绑定 CSR 公钥、消耗邀请并登记证书序列号；相同请求 ID 和相同 CSR 的重试只返回原结果，不得再次签发，其他重用拒绝。等待审批不消费为成功，邀请到期或取消后拒绝；响应不包含私钥。证书签发跨外部 CA 的事务须用持久化意图和幂等签发记录恢复，不得出现第二个有效身份。
4. 客户端证书专用 CA 签发，EKU 为 clientAuth；唯一 URI SAN 精确为 `urn:mcui:node:<node_id>`，当前实现的 `node_id` 是 `node-` 加 32 位小写十六进制。服务端验证客户端证书链、有效期、用途、URI SAN、CA/序列号映射、节点启用状态和证书当前状态；每次 Agent 请求均做应用层状态检查，已建立连接也不能绕过撤销。CSR 的其他 SAN 不采纳。Master 的 Agent 接口拒绝无 TLS、无效/撤销/禁用证书。
5. 在当前有效证书到期前通过 mTLS 请求轮换，提交新本地密钥 CSR 并验证持有权；新证书绑定同一 node_id，登记新序列号与明确重叠截止时间。先持久化新密钥和证书并验证新连接，确认后撤销旧证书；重叠最多 24 小时，超时旧证书无条件失效。轮换请求及响应幂等，失败保留未撤销且未过期的旧身份；撤销立即覆盖重叠。证书状态与节点状态每次请求检查。
6. 发现泄露立即禁用节点并撤销全部证书、停止签发/投递、审计和告警；已离线节点无法即时得知撤销，不能承诺远程即时停止。私钥丢失、过期或重装不得以旧邀请码自动恢复：操作员复核节点与本地控制权、撤销旧证书，创建新的受限一次性恢复邀请，经可信渠道人工引导；新身份使用新密钥。若本地防重放状态无法证明连续，按第 6 节隔离恢复，不能仅凭恢复邀请重开执行。
7. Master TLS CA/地址或消息验证密钥变更必须由现有受信任更新机制、版本防回退和双人审批授权，先分发新信任并确认再移除旧信任；旧根不可用或疑似失陷时，停止新授权，通过本地管理员及独立可信渠道重新引导，禁止网络自恢复。其具体签名信封、CA 运行参数与演练仍待单独规范，不得在其完成前启用远程根变更。

默认心跳/任务轮询 15 秒、在线超时 60 秒，随机抖动和指数退避；大小、超时、并发应有限制。服务端时间无法可信判断、明显回拨或超出允许偏差时拒绝新任务/配置并告警，不关闭校验。各端与受信时间源最大偏差定为 30 秒；过期检查不延长期限，恢复事务不依赖重新打开过期授权。

## 3. 通用签名编码与校验

V1 **仅使用 RFC 8785 JCS + 标准 Ed25519（RFC 8032，非 Ed25519ph）**。所有签名对象是 UTF-8 JSON，最外层 `signature` 为 64 字节签名的 RFC 4648 标准 Base64，保留 `=` padding；公钥是 32 字节原始 Ed25519 公钥。待签名输入为对应 ASCII 域字符串（包含末尾单个 `\n` 字节）拼接 `UTF8(JCS(删除顶层 signature 后的完整 JSON 对象))`，无 BOM、无额外换行、无预哈希。域分别为 `MCUI-TASK-V1\n`、`MCUI-CONFIG-V1\n`、`MCUI-CANCEL-V1\n`、`MCUI-SKIP-V1\n`。签名覆盖 `schema_version`、key ID、算法及所有其他字段；验签按对象种类固定域，不接受消息指定域或算法协商。

JSON 必须符合 I-JSON/JCS：UTF-8 严格解码，拒绝重复键（包括转义后同名）、无效 Unicode/孤立代理、非有限数、未知字段、null、类型错误或尾随数据；不得先归一化 Unicode。所有数字只允许 JSON 整数且在 0..9007199254740991 范围内，计数从 1 开始，禁止指数、小数形式；必须检测溢出。时间仅允许 UTC `YYYY-MM-DDTHH:MM:SSZ`，严格验证日历，不接受闰秒、偏移或小数秒。标识符除另述外使用 1..128 字节 ASCII `[A-Za-z0-9._:-]`；摘要为小写 64 位十六进制 SHA-256。签名 Base64 必须规范解码且长度准确。消息上限 64 KiB；配置原始字节上限 4 MiB。对所有对象必须验证版本为整数 `1`、`signature_algorithm` 精确为 `Ed25519`，并用受信任且具相应用途的 `signing_key_id` 查本地公钥；未知、撤销或不适用的 key 拒绝，严禁从消息自行取得信任。

时间满足 `issued_at <= not_before < expires_at`，接收时拒绝超过本地时间 30 秒的未来 `issued_at`；开始新操作须本地时间不早于 `not_before` 且严格早于 `expires_at`。本地时间无可信依据时暂停。消息先结构解析、校验签名、目标、密钥用途、时间和策略，再持久化和执行；未经认证或不合法的数据不能改变序号或状态。

## 4. 任务、配置和控制消息

以下对象所有列出字段均必填、无其他字段；字段名大小写敏感。每个任务 `task_id` 全局唯一，`node_id` 精确匹配本机；每节点序号自 1 连续分配。定义任务 body（示例未包含可用签名，**不是测试向量**）：

```json
{"schema_version":1,"task_id":"task-001","node_id":"node-001","sequence":1,"operation":"core.start","issued_at":"2026-11-16T08:00:00Z","not_before":"2026-11-16T08:00:00Z","expires_at":"2026-11-16T08:10:00Z","payload":{"core":"xray"},"approval_id":"approval-001","signing_key_id":"task-key-01","signature_algorithm":"Ed25519","signature":"<base64>"}
```

通用字段按第 3 节；`operation` 和 `payload` 严格对应且禁止扩展。`core` 仅 `xray`、`sing-box`、`mita`。V1 已定义以下结构；具体操作及 Helper 步骤未完成安全策略和实测前不得启用：

| operation | payload 必填字段（除 core 外） |
|---|---|
| `core.status` | 无；Phase 0 仅定义签名结构，运行时投递与执行仍未开始 |
| `core.start`, `core.stop`, `core.restart`, `core.uninstall` | 无 |
| `core.install`, `core.upgrade`, `core.downgrade` | `version`、`artifact_id` 为标识符；`manifest_version` 为正整数 |
| `config.apply` | `revision` 正整数、`content_sha256` 摘要、`core_version` 标识符 |

任务签名只授权固定动作；制品 ID、版本、架构及摘要须匹配独立受信任且未过期的发布清单，降级须独立授权。任务时间为启动与新步骤授权边界，不是可无限续租的通行证。Agent/Helper 自更新和信任根轮换的独立发布授权尚未定义，禁止用本表绕行。节点证书轮换走第 2 节身份接口而非通用任务。

**配置签名对象**必填字段：`schema_version`、`node_id`、`core`、`core_version`、`revision`、`content_sha256`、`content_size`、`issued_at`、`not_before`、`expires_at`、`signing_key_id`、`signature_algorithm`、`signature`。`revision` 在每 `(node_id, core)` 内正整数单调递增，`content_size` 为 0..4194304 的整数；摘要作用于精确原始配置字节，不做换行或 Unicode 转换。配置通过已认证通道单独取得，校验长度和摘要。应用须同时具备未过期 `config.apply` 任务，其 node/core/version/revision/hash 与配置签名逐字段一致；签名配置本身不是执行授权。主控与 Agent 都须按锁定 Core 版本、节点策略进行语义白名单验证，未知字段拒绝；候选预检低权限隔离运行。完成事务后持久化最高 revision、哈希和 LKG；低 revision 拒绝，同 revision 同 hash 仅可返回既有结果，不得重新触发；同 revision 不同 hash 为冲突。手动回滚生成更高 revision，即便内容与旧配置相同。失败恢复只恢复先前 LKG，不允许以此执行新配置。

**取消对象**字段：`schema_version`、`node_id`、`task_id`、`sequence`、`issued_at`、`not_before`、`expires_at`、`signing_key_id`、`signature_algorithm`、`signature`，使用任务用途密钥和取消域。取消须目标精确匹配；可独立于顺序任务领取并持久化。取消先于开始则任务消费为 CANCELED；已开始只在操作定义的安全点停止并回滚，无法安全中止时继续完成既有已授权步骤或安全恢复，返回 `CANCEL_TOO_LATE`，不能虚报取消成功。取消与开始由本地同一事务/锁线性化。

**缺口跳过对象**字段：`schema_version`、`node_id`、`sequence`、`reason`、`issued_at`、`not_before`、`expires_at`、`signing_key_id`、`signature_algorithm`、`signature`；`reason` 仅 `VOID_UNISSUED`、`EXPIRED`、`CANCELED`。仅当前期望序号可消费，必须验签且有效；Master 必须证明该序号未签发或已有不可启动的终态，不能借 skip 替换已启动任务。为避免跳过未知已开始任务，节点存在该序号 RUNNING/未决记录时拒绝 skip 并进入对账。跳过是独立签名的空槽声明，不是新任务或任意跳号授权；其序号和不可变内容须持久化。签发 skip 后不得再签发该槽任务。

## 5. 序号、租约、ACK 与持久化恢复

- Master 在事务中为每节点保留下一个连续序号及不可变任务/skip 槽，审批消费、任务内容与签发意图持久化；签名服务崩溃后只能重试同一内容，禁止对同一槽签发不同内容。签发后持久化签名，重复投递字节一致；分配后未签发的空槽只能通过审计的 skip 关闭。持久化失败不得投递。
- Agent 持久化 `next_sequence`，仅接受该序号；更大序号触发缺口补取，不能静默前移。较小序号仅在与已存对象的 task ID、签名字节及规范化内容一致时返回已存结果，否则报冲突并停止高风险操作。对期望序号的认证有效任务先原子保存完整信封、状态和序号，再 ACK；任务未开始即过期时持久化 EXPIRED 并消费该槽，不执行；无效签名或错误目标不消费。未来 not_before 的任务等待，不得跳过。
- ACK 记录 `(node_id, task_id, status_version)`；状态版本正整数单调递增，重复上报内容一致则幂等确认，相同版本不同内容为冲突；Master 校验证书节点与任务归属，ACK 丢失可重发。结果、错误和审计不得包含密钥、完整配置或令牌。
- Master 租约仅是投递协调，不是执行授权：每次投递返回租约 ID 与截止时间，租约到期只允许重投同一不可变任务，不能创建不同任务替代或假设原任务未执行。Agent 不因租约过期重启已完成步骤；签名有效期及本地状态决定是否允许启动。任务最终状态未经确认时先对账，不重复签发同一业务副作用。
- 本地事务在副作用前持久化任务、步骤意图和足以判定结果的标识，提交并保证落盘；执行后持久化观察结果和状态。进程重启先对账外部实际状态，再确定已完成、可安全恢复或 `NEEDS_RECONCILIATION`；无法证明的副作用不得盲目重试。任务在有效期内开始后，过期或离线仅允许完成已经持久化且明确授权的正在进行步骤、检查及安全回滚；未开始的后续特权步骤不得启动，除非另有新的有效授权。取消同理不自动授权新动作。
- Helper 通过受限 Unix socket 和 `SO_PEERCRED` 校验 Agent 身份，独立验证原始任务、节点、类型、签名、有效期与实际参数逐字段一致；使用 root 私有账本持久化 `(node_id, task_id, step_id)`、签名授权摘要、步骤意图与结果，定义固定步骤及顺序后才开放相应操作。Agent 的 ACK 或租约不能替代 Helper 验签；Helper 崩溃后先对账，拒绝重复副作用。步骤授权、恢复和参数绑定未实现时相应操作禁用。
- 状态为 `QUEUED`、`LEASED`、`ACK_ACCEPTED`、`RUNNING`、`VERIFYING`、`SUCCEEDED`、`FAILED`、`ROLLING_BACK`、`ROLLED_BACK`、`EXPIRED`、`CANCELED` 或 `NEEDS_RECONCILIATION`。成功须有操作对应的健康验证；回滚失败明确告警，不伪装成功。任何状态转换与结果均须持久化，终态只返回原结果。

## 6. 防回退与灾难恢复

Master 备份包括任务槽、签发意图和结果、每节点高水位、审批消费、证书和节点撤销、配置 revision、签名密钥信任及审计。备份加密、访问受限并保留独立追加的安全检查点。恢复旧备份后先冻结注册、签发、轮换和高危任务；不得仅凭恢复数据库的计数器继续。对照独立可信检查点和各节点/Helper 持久化账本，核对最高序号、未决任务、证书撤销、信任版本及配置 revision，补齐经验证的不可变记录；任何无法证明新鲜或无法排除曾签发不同内容的槽均隔离人工处理，不靠跳号掩盖。待完整对账并经授权安全管理员批准后才能恢复对应节点签发。

Agent 或 Helper 状态丢失、回滚、损坏或身份重装时暂停所有新副作用；保留运行中的 LKG，报告 `NEEDS_RECONCILIATION`。操作员通过可信本地控制与 Master 独立记录确认身份、任务及实际系统状态，恢复可信账本并取得明确批准；不能证明连续性时保持隔离，须经本地人工重建并建立不可复用的新节点身份和独立序号空间，旧身份全部撤销。不得仅复制高水位、重装证书或忽略未知副作用。信任根损坏按第 2 节人工引导；未完成检查点独立性、操作步骤和故障演练前不宣称恢复可用。

## 7. 测试向量规范及验收

当前版本化共享向量位于 `internal/protocol/testdata/protocol-v1.json`：覆盖 task、config、cancel、skip 各一个签名正例，含乱序字段的等价输入和 8 个负例。正例提供完整 JSON、JCS 文本、签名字节、公开测试 seed、公钥、签名 hex/Base64；配置向量还提供精确原始字节、长度及 SHA-256。固定 seed 仅为公开测试材料，绝不能用于生产。

Go 测试通过 `internal/protocol` 校验 schema、拒绝负例并比对规范化签名字节；`scripts/verify-protocol-vectors.mjs` 使用 Node.js `crypto` 与独立实现的 ECMAScript JSON 规范化逻辑校验同一向量。当前已有两种语言/密码实现的互操作证据，但尚未完成独立安全评审、向量责任人复核或全部 I-JSON/JCS 通用规范向量验收；不能据此宣称阶段 0 退出。

每个正向量必须给出：向量 ID、对象类别和域前缀的精确 UTF-8 十六进制、完整输入 JSON、删除顶层签名后的 JCS 精确 UTF-8 文本及十六进制、完整待签名字节十六进制、32 字节公钥十六进制、测试私钥材料及其格式、64 字节签名十六进制与规范 Base64、预期验签结果；配置向量另附原始配置字节十六进制、长度和 SHA-256，以及与任务绑定的字段。分别覆盖 task、config、cancel、skip，包含字段乱序、转义和合法边界整数；重序和等价 JSON 表示应得到一致 JCS 和签名输入。非 ASCII 测例属于独立 JCS 规范化组件测试，当前协议字段不允许非 ASCII，不能将其作为协议对象正向量。

负向量至少覆盖：单字节修改签名或载荷、错误公钥/用途/域、错目标、重复键及转义后重复键、非法 UTF-8/孤立代理、额外字段、null、未知版本/算法、非规范 Base64、超长/越界/小数/指数、时间边界及过期、配置字节/长度/hash 不一致、revision 回退、同序号不同内容、skip 覆盖运行中任务。所有失败应注明预期拒绝层级且不得改变持久化状态或产生特权副作用；签名正确但语义越权配置仍须拒绝。

集成与故障注入应覆盖邀请竞争与重试、CSR 持有证明、伪造服务器、证书过期/禁用/轮换重叠及已建立连接撤销、时钟回拨、序号缺口补取、过期消费、取消与启动竞争、租约到期重复投递、ACK 丢失、每一步断电/磁盘满、Helper 重放、Master/节点旧备份恢复、LKG 恢复和不可判定状态隔离。结果须记录真实环境与证据，不以本设计文档代替执行结果。

## 8. 未完成项与发布阻断

1. 本文仍为阶段 0 协议草案。签名 schema/parser、向量和跨实现规范化/验签已部分实现；尚无形式化 JSON Schema、独立安全评审或完整故障演练，阶段 0 退出条件未满足。
2. 任务签发服务、审批矩阵、密钥保管与轮换控制信封、可信时间源、证书 CA 参数、注册接口细节、备份检查点和人工恢复操作仍需配套设计及审查；在具备可验证的完整机制前不得启用依赖功能。
3. Helper 各操作步骤/重试和各 Core 版本语义策略、制品信任链、Agent/Helper 自更新独立授权、配置与 Core 真实恢复行为尚未验证；相关远程操作必须保持禁用。现有任务信封缺少 Helper 精确参数绑定所需的步骤、制品摘要、架构及期望状态。`core.status` 目前只是 schema 与公开签名向量，不存在阶段 2 的投递 API、Agent 执行器或 Helper。首次收到已过期任务、预先取消与 skip 的竞争、next_sequence 推进时机及崩溃恢复的线性化状态转换尚未冻结；不得将当前草案用于任务实现或验收。
4. 制品信任方案采用 [TUF 决议草案](./artifact-trust.md)，尚待实现选择、密钥保管人批准及互操作验证。本协议不改变完整 V1 的逐 Core 支持矩阵与发布门槛。
