# Core 制品校验

Xray 安装使用固定的官方 GitHub Releases 来源。管理员在主控面板选择一个已发布的稳定版本，Master 根据节点架构查找对应官方资产，并把精确版本、架构和 SHA-256 写入专用生命周期签名任务。节点不需要 Core 发布公钥或签名清单。[版本选择与发布](./phase-3-release.md)

## 1. 版本解析与摘要绑定

Master 和节点只访问代码中固定的 `XTLS/Xray-core` 仓库，不接受任务或面板提交任意下载 URL。版本标签必须是已发布的稳定三段版本，资产名称必须匹配该版本和 Linux amd64/arm64 架构。

Master 优先使用 GitHub Release API 给出的资产 SHA-256。若 API 未提供摘要，Master 从官方 Release 下载完整资产并计算 SHA-256。随后 Master 使用 Xray 生命周期任务密钥签署节点、动作、版本、架构和摘要。这样发布者无需为每个 Core 版本单独维护一份清单。

Agent 和 Helper 各自验证签名任务，再向固定官方 Release 地址解析相同版本和架构。若 API 提供摘要，节点要求它与任务摘要一致；无论 API 是否提供摘要，下载后的实际字节长度和 SHA-256 都必须与签名任务完全相同。官方源不可用时，可按当前有效任务和租约从 Master 请求摘要完全匹配的备用缓存。

## 2. 安装边界

- Release 标签、资产文件名和下载 URL 必须符合固定映射，拒绝草稿、预发布、重复资产、错误架构和非官方主机。
- 下载受大小、超时和重定向限制；安装前按精确长度和 SHA-256 校验，并限制 ZIP 条目数量、路径、文件类型和解压大小。
- 候选 Core 在固定低权限 systemd 环境中预检。激活失败时恢复上次提交的二进制和运行状态。
- 任务签名只授权精确操作和制品摘要，不提供通用命令或任意 URL。

这套信任链依赖 GitHub 官方账户、API/TLS 和项目生命周期签名密钥；它不提供独立离线审核者对上游二进制的额外签名背书。任务摘要能阻止签发后的字节替换，但不能证明上游构建过程没有被攻破。管理员可按兼容矩阵选择需要的已发布版本。

Agent/Helper 的自身成对更新继续使用独立发布签名和节点更新授权；该流程与 Core Release 版本选择分开。[成对更新](./phase-3-runtime-update.md)。旧 TUF 和 Core 清单代码仅保留用于历史部署及兼容验证，不是新安装的前置条件。
