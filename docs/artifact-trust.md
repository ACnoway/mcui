# 制品信任方案（阶段 0 决议基线）

状态：TUF 客户端及发布工具使用锁定的官方 `go-tuf/v2 v2.4.2`。发布工具支持分角色签名和校验后的版本化仓库输出。实际生产保管人、信任根及上线的 HTTPS 仓库待部署。[TUF 发布手册](./phase-3-release.md) · [依赖版本](https://github.com/theupdateframework/go-tuf/releases/tag/v2.4.2)

## 1. 方案与角色

离线根角色 2-of-3 独立保管人，targets 2-of-3 独立发布审核人，snapshot 和 timestamp 各 1-of-1 在线专用密钥。根私钥保留在带外签名环境。Core 与 Agent/Helper 使用互不重叠的 `core-targets` 和 `runtime-targets` 委派及独立密钥，各 2-of-3。单人不得同时控制同一角色阈值。高危任务仍须单独审批。

通过已验证的线下渠道在安装包中引导可信 TUF root，核对公钥指纹，包本身也必须通过独立可信渠道校验；不得通过首次联网自动信任根。TUF 元数据按所选规范实现标准签名封装和规范化，任务/配置签名另遵循其协议，不能混用或自行改写 TUF 格式。

### 官方版本目录与安装授权

Master 的只读目录从固定的官方 GitHub Releases API 获取版本和资产信息：`XTLS/Xray-core`、`SagerNet/sing-box`、`enfein/mieru`。它用于面板版本发现，不代表发布已审核、资产可信或允许安装。GitHub API 的资产 `digest` 字段如存在会以 SHA-256 显示；它是上游提供的摘要信息，不替代本项目 TUF targets 的阈值签名和独立审核。Master 另外为每个 Core 缓存最新稳定版的 amd64/arm64 官方制品，并在下载时按该 API digest 和长度校验；该副本只为未来精确匹配的备用下载预留，不触发安装，也不接受目录响应直接变成任务 URL。未来常规下载仍由 Agent 直连固定官方源。备用缓存和版本目录实现限制见[阶段 3 进度](./phase-3-progress.md)。

### 客户端实现范围

- 客户端只接受经离线渠道配置的初始 `root.json`、固定 HTTPS metadata origin 和已通过认证 NTS 健康检查的主机时钟；没有网络首次信任或任务提供的 URL。它用 `go-tuf/v2` 完成 root、timestamp、snapshot、targets 和按需委派 targets 的标准 TUF 客户端流程。
- 每次解析都从离线引导 root 顺序验证本地保存的 root 轮换记录，再刷新上游元数据。新 root 经旧/新阈值链验证后按版本原子追加到独立私有目录，即使后续角色刷新失败也保留已接受的轮换。元数据、root 历史和制品缓存使用互不嵌套、无符号链接的 `0700` 目录。独立于节点本地状态的单调检查点仍待实现。
- target 路径由固定 Core、精确版本和本机 Linux 架构生成。TUF 自定义字段必须逐项绑定内容寻址的制品 ID、Core、版本、OS、架构、`upstream-prebuilt` 构建来源、固定归档格式、固定上游 source ID、审核记录 ID 及上游签名事实状态；未知/重复字段、无审核 ID、非 SHA-256、空/超 512 MiB target 均拒绝。该签名事实状态是已签 TUF 审核记录中的声明，不代表客户端独立验证了上游签名。
- 二进制只从该 Core 的固定 GitHub Release asset URL 下载；最多 5 次 HTTPS 跳转至 GitHub 官方资产/CDN 主机，禁用代理，DNS 结果只拨号到公网单播地址。字节数和 SHA-256 与已验证 target 不符时丢弃临时文件。成功文件按摘要写入私有缓存，权限为 `0400`，采用不覆盖的链接发布。
- 节点本地 `mcui-xray` 要求独立委派的 `core-targets` 直接授权目标，校验 root 与 targets 阈值和角色密钥分离。工具在激活前通过同一文件描述符复验归档，完成隔离预检并再次确认 TUF 授权。生产签名材料、审核记录保管和 Agent/Helper 远程授权仍待部署或实现。[阶段 3 操作说明](./phase-3-operations.md)

## 2. 入库与消费

发布审核固定上游项目、版本、来源、上游认证方式、原始制品与摘要、许可证、构建选项、平台、审核人和证据。若上游提供可验证签名，离线核验官方信任根及签名并记录证据；未提供或无法核验时明确标记，独立审核来源/构建后方可内部签名，内部签名不证明上游签名有效。未经审核或无证据不发布。

TUF targets 自定义元数据绑定唯一制品 ID、Core、精确版本、Linux、架构、构建选项、归档格式、来源 ID 与审核证据；标准 target 元数据绑定长度和 SHA-256。任务绑定同一制品 ID、版本及清单版本/摘要；节点与 Helper 独立验证授权和元数据，严格匹配本机平台及实际字节。源地址仅由 root 管控的固定 HTTPS 源映射确定，不接受任务 URL；限制重定向到已允许的 HTTPS 主机、解析后的网络地址、超时、大小和并发，禁止本地文件及非预期内网/元数据地址。

新安装或升级须验证完整 TUF 链、阈值、版本、有效期、目标长度/摘要及授权，时钟异常或 metadata 过期、无法刷新时失败关闭；已运行 LKG 不因离线自动停止。root 私有持久化记录各角色已见最高版本及事务状态，防止旧元数据回滚；恢复旧备份无法证明新鲜度时冻结写操作，凭可信当前状态及人工审核恢复，不得重置计数绕过防回滚。

限制归档压缩/展开大小、数量、深度和时间；拒绝绝对路径、`..`、所有链接、设备文件、特殊权限、重复目标及脚本/安装钩子。Helper 从安全文件描述符重新校验并在 root 拥有目录暂存，防止 TOCTOU；固定低权限隔离环境执行允许的预检。原子切换后健康检查，失败恢复 LKG，恢复失败明确告警并停止重试。

## 3. 轮换、撤销和降级

按 TUF root 顺序更新及旧根/新根各自阈值验证；替换 targets、snapshot、timestamp 密钥由有效 root 授权，审计并验证新链。泄露时暂停受影响发布、隔离密钥、撤销/替换并重新签发元数据；旧根阈值不可用时只允许本地人工通过独立可信渠道重新引导根，禁止远程静默重置信任。离线节点在信任可恢复前不得接受新安装。

Core 降级不是 TUF 元数据降级：须显式签名任务、独立高危审批，绑定节点、Core、精确版本、制品摘要、有效期和一次性授权；旧制品仍须出现在当前未过期 targets 且未撤销。事务内恢复已记录 LKG 不等于开放任意历史版本；仅在原事务授权范围内恢复并记录。Agent/Helper 更新须独立发布角色与高权限任务、监督健康确认和本地恢复；未完成演练前禁用远程更新。

## 4. 可测试验收（均待执行）

| 场景 | 预期 |
|---|---|
| 修改 targets 或不足阈值签名 | 拒绝，无安装副作用 |
| 过期 timestamp、旧 snapshot、时钟回拨或旧备份 | 拒绝新安装并告警，运行中 LKG 保持 |
| 替换目标字节、大小、架构或任务绑定 | Agent 和 Helper 任一不匹配即拒绝 |
| 未批准来源跳转、归档穿越/链接/炸弹 | 中止且不写目标目录 |
| 未授权降级、已撤销目标、根轮换缺旧/新阈值 | 拒绝 |
| 写满磁盘/断电/健康检查失败 | 对账恢复 LKG；无法恢复时明确失败 |

设计基线已冻结：TUF；离线 root 与 targets 角色阈值为 2-of-3；snapshot/timestamp 各使用分离的单用途在线密钥；Core 与 Agent/Helper targets 分离委派；过期/时钟异常时拒绝新安装，运行中 LKG 保持；降级要求目标仍受当前元数据信任并另有一次性独立审批。组织仍须任命实际密钥持有人和恢复责任人。Go 客户端实现版本已锁为 `go-tuf/v2 v2.4.2`；生产 key fingerprint、信任根离线引导包、发布/审核流程、互操作测试和项目内安全检查 **待确定/待验证**；主控备用副本目前只按上游 GitHub API digest 校验，不能替代这些信任步骤。本文件不代表任何制品已可信，也不构成阶段 0 签核。
