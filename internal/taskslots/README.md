# Task slot repository

This standalone database is not wired to the Master or any task API. `Init(path)` exclusively creates a database; `Open(path)` requires an existing, initialized v1 database and checks its schema. Always use a protected, dedicated persistent path and back up and restore this database together with the rest of the system. Never reinitialize a lost or stale database: restoring an old snapshot can reuse task IDs and sequence numbers and requires an external recovery/reconciliation procedure. Failed initialization can leave a file that must be inspected and explicitly removed before retrying.

`Reserve(nodeID, taskID, intent)` atomically stores the exact nonempty intent bytes, assigning a per-node sequence in the protocol range 1..9007199254740991; exhaustion fails closed without inserting a slot. IDs are globally unique for the lifetime of this database. A byte-identical retry for the same node and ID returns the original slot (including its completion state); altered intent, a reused ID, or a different task while that node has an active slot returns `ErrConflict`. Different nodes progress independently. Intent serialization and its protocol semantics are the caller's responsibility.

`Complete(nodeID, taskID, sequence)` marks precisely that slot terminal and is idempotent. It does **not** authenticate, authorize, verify a result, or distinguish success from failure. The future integration must first authenticate the node and authorize/validate the terminal result; untrusted callers must never have direct access to this method or database. Completion is not cancellation, skip, delivery, signing, approval, or execution. No such mechanism is implemented here. A caller should not mark complete merely because delivery occurred.

SQLite transactions use immediate write locking, DELETE rollback journals, and synchronous=EXTRA, with a ten-second busy timeout. Other journal modes are rejected, not migrated. Initialization syncs the containing directory. A failed mutation can have an uncertain outcome; callers must fail closed and reconcile before proceeding. `Open` rejects invalid stored values, gaps in each node's sequence starting at one, and an active record older than a later record. These checks are not a trusted checkpoint: deletion of a complete suffix, deletion of an entire node's records, or restoration of an internally consistent older database cannot be detected. Fail closed when rollback or state loss is suspected; safe deployment requires an independently protected, durable checkpoint and reconciliation procedure, which this package does not implement. A checkpoint must be integrated with the wider system's recovery protocol before claiming rollback detection; a second file restored with the database is not independent.

The abrupt-exit test checks process-exit recovery after commit, not power-loss durability; it does not simulate volatile-cache loss, torn writes, or storage faults. Operational errors must fail closed; do not replace or reset this database automatically. Concurrency and crash durability depend on a filesystem and storage stack honoring SQLite locking and sync guarantees. This package does not protect against privileged database tampering, disk loss, rollback, or external modification while running.
